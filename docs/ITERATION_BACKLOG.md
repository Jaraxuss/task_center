# 本地轻量任务中心 Iteration Backlog

## 1. 文档目标
本文件沉淀 MVP 完成后的下一轮迭代建议，帮助团队按业务价值和技术收益排优先级，而不是凭感觉乱加功能。

---

## 2. 迭代原则
- 先补强单用户本地闭环，再扩外部集成。
- 先补“高频刚需”，再补“看起来高级”。
- 先补“减少手工操作”的能力，再补“锦上添花”的表现层。

---

## 3. P1：MVP 后应优先进入的迭代

## 3.1 聊天接入层正式化
### 价值
当前产品目标明确要求用户可通过聊天自然语言创建/调整/取消/完成任务。MVP 可以只预留 source 和 nightly review 能力，但下一轮应该把聊天接入正式打通。

### 建议能力
- 从聊天消息创建任务
- 从聊天消息修改时间和状态
- 从聊天消息创建提醒
- 记录 message_id / session_id，支持消息回溯

### 技术建议
- 增加 `source_ref`、`external_message_id` 等字段
- 聊天解析与任务写库之间增加 adapter/service 层

## 3.2 晚间收口完整闭环
### 价值
22:00 收口是产品特色，不应只停留在“后端能支持”。

### 建议能力
- 生成 nightly review session 记录
- 跟踪“已发送 / 已回复 / 已处理 / 部分失败”状态
- 可查看某天收口结果
- 支持人工补处理失败项

### 技术建议
新增 `nightly_review_sessions` 表，避免所有上下文都塞到 task_events 里。

## 3.3 提醒调度器
### 价值
MVP 只有 reminder 数据结构不够，下一轮应真正触发提醒。

### 建议能力
- 扫描待触发提醒
- 发送 chat 通知
- 记录 fired / failed 状态
- 支持取消未触发提醒

### 技术建议
- 使用 APScheduler / cron + worker
- reminder 触发写入 `reminder_fired` 事件

## 4. P2：体验增强型迭代

## 4.1 看板拖拽
### 价值
提升任务流转效率。

### 注意
- 只有在状态机和事件日志稳定后再做。
- 拖拽不应绕过专用状态接口。

## 4.2 更强的筛选与搜索
### 建议能力
- 多标签筛选
- 项目筛选
- 时间范围筛选
- 全文搜索标题/描述/事件备注

## 4.3 今日视图分组
### 建议能力
- 上午 / 下午 / 晚上分组
- 已过期任务单独高亮
- 无时间任务分组到底部

## 4.4 历史时间线优化
### 建议能力
- 按日聚合事件
- 展示状态变化轨迹
- 支持查看延期理由、完成备注

---

## 5. P3：结构升级型迭代

## 5.1 重复任务规则
### 场景
例如每日复盘、每周报销、每月对账。

### 建议能力
- daily / weekly / monthly 基础规则
- 生成实例任务
- 跳过某次执行

## 5.2 多项目与轻量统计
### 建议能力
- 项目维度任务统计
- 完成率
- 延期率
- 今日完成数 / 本周完成数

## 5.3 附件与引用
### 建议能力
- 任务挂网页链接
- 任务挂文档链接
- 任务挂聊天上下文链接

---

## 6. P4：外部集成型迭代

## 6.1 飞书 / Notion / Bitable 同步
### 价值
把任务结果同步到已有工作流中。

### 风险
- 字段映射复杂
- 同步冲突处理麻烦
- 会明显提高系统复杂度

结论：应在本地任务闭环稳定后再做。

## 6.2 日历集成
### 建议能力
- 将带 due_at 的任务推送到日历
- 从日历事件反向生成任务

---

## 7. 建议新增数据模型
以下模型不要求 MVP 立即实现，但下一轮很可能会需要：

### 7.1 nightly_review_sessions
| 字段 | 说明 |
|---|---|
| id | 收口会话 ID |
| review_date | 收口日期 |
| sent_at | 发送时间 |
| replied_at | 用户回复时间 |
| status | sent / replied / processed / failed |
| raw_reply | 用户原始回复 |
| parsed_payload_json | 解析结果 |
| created_at | 创建时间 |
| updated_at | 更新时间 |

### 7.2 task_source_refs
| 字段 | 说明 |
|---|---|
| id | 主键 |
| task_id | 任务 ID |
| source_type | chat / import / api |
| source_ref | 外部引用 |
| created_at | 创建时间 |

---

## 8. 推荐优先级路线图

### 第一个版本后，最合理的顺序
1. 聊天接入正式化
2. 晚间收口完整会话化
3. 提醒调度器
4. 更强筛选与搜索
5. 看板拖拽
6. 重复任务
7. 外部同步

原因很简单：前三项是在补产品闭环，后四项更多是在扩展能力边界。

---

## 9. 不建议过早做的事
- 多用户与权限
- 复杂 AI 任务拆解
- 任务依赖关系图
- 甘特图
- 很重的统计大盘
- 同时接很多外部平台

这些东西都容易让项目从“轻量任务中心”膨胀成“半个项目管理系统”。那条路很热闹，也很容易把人带沟里。

---

## 10. 结论
MVP 后最值得做的，不是把 UI 继续抛光，而是把“聊天创建任务 + 晚间收口 + 提醒触发”三件事闭环掉。做到这一步，这个系统才真正像一个可长期使用的本地任务中心，而不是一个能改 CRUD 的漂亮壳子。
