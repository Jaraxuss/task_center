# 本地轻量任务中心 MVP PRD

## 1. 文档目标
本 PRD 用于锁定“本地轻量任务中心”MVP 产品范围，统一前端（React）与后端（FastAPI + SQLite）对核心对象、页面、状态流转、晚间 22:00 收口规则和验收标准的理解，避免开发过程中的边界漂移。

---

## 2. 产品目标与非目标

### 2.1 产品目标
构建一个运行在本地的轻量任务中心，满足以下核心诉求：
1. 用户可以继续通过聊天自然语言创建、调整、取消、完成任务与提醒。
2. 用户可以在浏览器中查看今天任务、状态看板、历史记录，并做直接操作。
3. 系统能够支持每日 22:00 的“晚间收口”流程，对当日任务进行归档、完成确认和延期处理。

### 2.2 非目标（MVP 不做）
- 多用户与权限系统
- 飞书 / Notion / Bitable 同步
- 复杂自然语言解析引擎
- 高级重复任务规则
- 移动端 App 与推送体系
- 完整统计分析报表

---

## 3. 目标用户与使用场景

### 3.1 目标用户
当前 MVP 面向单用户本地使用，默认只有一个任务拥有者。

### 3.2 核心使用场景
1. **快速记任务**：聊天中随手添加“明天下午 3 点给客户回电话”。
2. **白天执行任务**：在浏览器中查看今日任务列表，快速完成、延期、改时间、加提醒。
3. **回顾与追踪**：在历史视图中查看任务的状态变化与变更日志。
4. **晚间收口**：22:00 用户对未完成项进行说明，系统基于回复自动完成或延期处理。

## 4. 用户故事

### 4.1 创建与查看
- 作为用户，我希望能创建一个任务，并设置标题、描述、截止时间、标签和项目，以便把事情记下来。
- 作为用户，我希望今日视图默认只看今天相关任务，并按时间排序，方便安排执行顺序。
- 作为用户，我希望在看板中按状态查看任务，快速定位正在做、待做、延期中的事项。

### 4.2 编辑与执行
- 作为用户，我希望点击任务后可直接修改时间、状态、提醒，而无需跳转多个页面。
- 作为用户，我希望一键标记任务完成。
- 作为用户，我希望可以延期任务，并记录延期到什么时间、为什么延期。
- 作为用户，我希望取消任务时保留取消记录，而不是直接删除。

### 4.3 提醒
- 作为用户，我希望一个任务可以有多个提醒，例如提前 30 分钟和准点提醒。
- 作为用户，我希望能看到提醒的状态：已计划、已触发、已取消。

### 4.4 历史与追踪
- 作为用户，我希望每次关键操作都被记录下来，便于事后追溯发生了什么。
- 作为用户，我希望在历史视图按日期、状态、关键词检索过往任务。

### 4.5 晚间收口
- 作为用户，我希望每天 22:00 系统能组织我处理今日未完成事项。
- 作为用户，我希望在回复晚间收口后，只列出我未完成或需要延期的事项，减少重复输入。
- 作为用户，我希望系统对我未提及的今日待办自动完成，但前提是我已对收口消息做出回复。

## 7. 核心页面定义

## 7.1 今日视图（Today）
### 目标
让用户最快看到“今天需要处理什么”，优先支持日常执行。

### 展示规则
- 默认显示与“今天”相关的任务：
  - due_at 落在今天
  - 或 deferred_to 落在今天
- 默认按时间升序排序，时间为空的任务排在最后
- 已取消任务默认折叠或隐藏
- 已完成任务可展示在列表底部或单独分组

### 支持操作
- 新建任务
- 打开任务详情
- 快速完成
- 快速延期
- 快速改时间

### 列表字段建议
- 标题
- 时间（due_at / deferred_to）
- 状态
- 标签
- 项目
- 是否有提醒

## 7.2 看板视图（Board）
### 目标
让用户从状态维度管理任务。

### 分组列
- todo
- doing
- deferred
- done
- canceled

### 支持操作
- 查看某状态下任务
- 点击进入详情
- 可选：MVP 不要求拖拽，先用按钮变更状态

## 7.3 历史视图（History）
### 目标
支持回顾与检索。

### 支持筛选
- 日期范围
- 状态
- 关键词（标题 / 描述）
- 来源 source（可选）

### 展示内容
- 历史任务列表
- 每个任务最近更新时间
- 点击进入详情查看完整事件流

## 7.4 任务详情（Task Detail）
### 模块组成
1. 基本信息：标题、描述、项目、标签、来源
2. 状态信息：当前状态、创建时间、更新时间、完成时间、取消时间
3. 时间信息：due_at、deferred_to
4. 提醒信息：提醒列表、提醒状态
5. 操作区：完成、延期、取消、改时间、新增提醒
6. 事件日志：按时间倒序或正序展示

## 8.1 Task 字段定义
| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| id | string / integer | 是 | 任务唯一标识 |
| title | string | 是 | 任务标题，建议 1~120 字 |
| description | text | 否 | 任务补充描述 |
| due_at | datetime nullable | 否 | 计划执行/截止时间 |
| status | enum | 是 | todo / doing / done / deferred / canceled |
| project | string nullable | 否 | 所属项目或分类 |
| tags_json | json array | 否 | 标签数组 |
| source | enum | 是 | chat / web / system |
| created_at | datetime | 是 | 创建时间 |
| updated_at | datetime | 是 | 最近更新时间 |
| completed_at | datetime nullable | 否 | 完成时间 |
| canceled_at | datetime nullable | 否 | 取消时间 |
| deferred_to | datetime nullable | 否 | 延期后的目标时间 |

### 字段约束
- `title` 不能为空。
- `status=done` 时，`completed_at` 应有值。
- `status=canceled` 时，`canceled_at` 应有值。
- `status=deferred` 时，`deferred_to` 应有值。
- `tags_json` 在 API 层对前端暴露为 `tags: string[]`，不暴露底层存储实现。

## 9. 状态机设计

## 9.1 任务主状态
- `todo`：待处理
- `doing`：进行中
- `done`：已完成
- `deferred`：已延期，等待新的执行时间
- `canceled`：已取消

## 9.2 状态流转
```text
todo -> doing
todo -> done
todo -> deferred
todo -> canceled

doing -> done
doing -> deferred
doing -> canceled

deferred -> todo
(deferred 到期后可手动或系统恢复为 todo)
deferred -> doing
deferred -> done
deferred -> canceled

done -> (不允许直接回退，MVP 默认不支持)
canceled -> (不允许恢复，MVP 默认不支持)
```

## 9.3 业务规则
- 修改 `due_at` 不必然改变状态。
- 执行延期操作时：
  - 状态置为 `deferred`
  - 写入 `deferred_to`
  - 追加 `task_events` 事件
- 执行完成操作时：
  - 状态置为 `done`
  - 写入 `completed_at`
  - 追加 `completed` 事件
- 执行取消操作时：
  - 状态置为 `canceled`
  - 写入 `canceled_at`
  - 追加 `canceled` 事件

### 关于 nightly_review_pending
MVP 不新增主状态字段值，避免污染任务主状态机。晚间收口中的“待确认”由查询条件和事件来表达：
- 条件：当日任务且 22:00 时仍为 `todo/doing/deferred` 的任务
- 事件：`nightly_reviewed`
- 后端可在聚合接口中返回 `needs_nightly_review: boolean`

## 10. 晚间 22:00 收口规则

## 10.1 业务目标
在每天 22:00 对“今日仍未收口”的任务进行一次统一处理，减少用户逐个点任务的成本。

## 10.2 参与收口的任务范围
满足以下条件的任务进入晚间收口候选集：
1. 与今天相关：
   - `due_at` 在今天，或
   - `deferred_to` 在今天
2. 当前状态属于：`todo`、`doing`、`deferred`
3. 未在当天 22:00 之后完成/取消

## 10.3 收口交互规则
1. 22:00 由聊天侧发起收口消息，列出今日未完成任务。
2. 用户回复本次收口消息后，系统解析用户提及的未完成项和延期时间。
3. **前提条件：用户已对收口消息做出回复。**
4. 在该前提下：
   - 用户明确提及“未完成/延期”的任务：更新为 `deferred` 或保留未完成并写入新时间。
   - 用户明确提及“取消”的任务：置为 `canceled`。
   - 用户明确提及“已完成”的任务：置为 `done`。
   - **用户未提及的今日待办：自动标记为 `done`。**

## 10.4 自动完成规则的边界
自动完成只在以下条件同时满足时生效：
- 本次 22:00 收口消息存在
- 用户已回复该次收口消息
- 任务属于本次收口候选集
- 该任务未被用户在回复中单独提及为未完成 / 延期 / 取消

若用户未回复，则：
- 不自动完成任何任务
- 原状态保持不变
- 后端可保留“待收口”记录供次日查看

## 10.5 数据记录建议
每次晚间收口完成后，为被处理任务写入 `nightly_reviewed` 事件，payload 建议包含：
```json
{
  "review_date": "2026-03-19",
  "review_session_id": "nightly-2026-03-19",
  "review_source": "chat",
  "action": "auto_done | defer | cancel | explicit_done | untouched_no_reply",
  "note": "用户回复中未提及，自动完成"
}
```

## 11. 异常场景

## 11.1 任务创建/编辑异常
1. 标题为空：前端禁止提交，后端返回 400。
2. 时间格式非法：后端返回 422。
3. 修改不存在的任务：后端返回 404。

## 11.2 状态操作异常
1. 已完成任务再次完成：后端返回 409 或幂等成功（MVP 建议幂等成功并返回当前状态）。
2. 已取消任务再次取消：同上。
3. 对已完成/已取消任务执行延期：返回 409。
4. 延期但未提供 `deferred_to`：返回 400。

## 11.3 提醒异常
1. 对不存在任务添加提醒：404。
2. 添加过去时间的提醒：400。
3. 重复提醒时间：MVP 可允许，不做去重。

## 11.4 晚间收口异常
1. 用户未回复收口消息：不触发自动完成。
2. 用户回复内容无法解析：
   - 保留原状态
   - 记录 review 失败原因
   - 可人工补处理
3. 收口过程中某任务写库失败：
   - 记录错误日志
   - 不影响其他任务处理
   - 对失败任务保留原状态，待人工重试

## 12. 验收标准

## 12.1 功能验收
### 任务管理
- 可以创建任务，至少支持标题、描述、时间、标签、项目。
- 可以编辑任务基本信息。
- 可以完成、延期、取消任务。
- 每次关键操作均写入事件日志。

### 提醒管理
- 一个任务可新增多个提醒。
- 提醒可展示状态。
- 任务详情能查看提醒列表。

### 视图
- 今日视图可展示当天任务，并按时间排序。
- 看板视图可按状态分组展示任务。
- 历史视图可查看历史任务和变更记录。

### 晚间收口支撑
- 后端能查询“今日待收口任务集合”。
- 能记录 nightly_reviewed 事件。
- 能在用户已回复前提下，对未提及的任务执行自动完成。

## 12.2 接口验收
- React 前端所有数据均来自 API，不写死 mock。
- FastAPI 提供稳定 REST API。
- 核心接口具备成功/失败示例与错误码定义。

## 12.3 工程验收
- 前后端本地可独立启动。
- SQLite 数据库可初始化。
- 目录边界清晰，前后端尽量少改共享文件。
- 至少有一份联调说明文档。

## 14. 决策结论
- MVP 的核心是“任务可见、可改、可收口”，不是“聊天解析很智能”。
- 晚间收口采用“用户已回复才自动完成未提及任务”的保守策略，避免误判。
- 主状态机保持简单，不为 nightly review 新增永久状态值。
- 前端优先打通 Today + Task Detail，后端优先提供稳定数据模型与事件日志能力。
