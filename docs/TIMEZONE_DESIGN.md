# Task Center 时区设计说明

## 1. 目标

本文档定义 `task_center` 当前统一采用的时间语义，避免再次出现：

- 数据库存的时间格式与后端假设不一致
- 前端按浏览器本地时区解释，导致展示错位
- 直接写库时把 naive / aware datetime 混用
- “北京时间 09:30” 被存成一套、显示成另一套

一句话原则：

> **数据库统一存 UTC aware 时间；接口统一传 ISO 8601；前端展示与按日分组统一按 `Asia/Shanghai`。**

---

## 2. 统一约定

### 2.1 数据库存储约定
- 所有核心时间字段统一以 **UTC** 存储
- 存储格式统一为带时区 ISO 字符串，例如：
  - `2026-04-08T01:30:00Z`
  - `2026-04-07T09:08:50.898439Z`
- 不再依赖“无时区 naive datetime + 口头约定”来推断真实语义

### 2.2 API 约定
- 后端返回时间时，统一返回 **ISO 8601 UTC** 字符串
- 典型格式：
  - `2026-04-08T01:30:00Z`
- 前端向后端提交时间时，也统一提交 ISO 8601 字符串
- 用户从 `datetime-local` 输入框输入“北京时间 09:30”时，前端应显式转成：
  - `2026-04-08T01:30:00Z`

### 2.3 展示与分组约定
- 页面展示默认按：`Asia/Shanghai`
- “今天 / 明天 / 某一天” 的判断，也统一按：`Asia/Shanghai`
- 不允许直接用：
  - `slice(0, 10)` 盲切日期
  - `new Date(value)` 后按宿主默认时区直接推断业务日期

---

## 3. 为什么要这样定

之前 `task_center` 的时间体系存在三个问题：

1. **数据库字段历史上按 naive datetime 使用**
   - ORM 也默认按 `timezone=False` 思路建模
   - 实际上系统使用者默认看的是北京时间

2. **前后端对时间的解释不统一**
   - 后端有些逻辑按本地约定时间理解
   - 前端有些逻辑按浏览器默认时区理解
   - 一旦开始引入 UTC 写入，就容易出现“触发时间对，显示时间错”

3. **直接写库时风险很高**
   - naive / aware datetime 混用后，排序、比较、分组都可能炸
   - 例如 Python 会直接报：
     - `can't compare offset-naive and offset-aware datetimes`

因此现在统一切换成：

- **存储：UTC aware**
- **业务展示：Asia/Shanghai**

这是最稳、也最容易长期维护的方案。

## 5. 输入语义

### 5.1 用户输入时间
当用户说：

- “明天上午 9 点半”
- “4 月 8 日 09:30”

在 `task_center` 里默认按：

- **Asia/Shanghai** 理解用户意图

然后转成 UTC 再存库。

例如：

- 用户意图：`2026-04-08 09:30 Asia/Shanghai`
- 存库值：`2026-04-08T01:30:00Z`

### 5.2 前端表单输入
`datetime-local` 没有时区信息，因此前端必须显式执行：

1. 把输入值视为 **Asia/Shanghai 本地时间**
2. 再转换成 UTC ISO 传给后端

错误做法：

- 直接 `new Date(value)` 然后让浏览器自己猜

正确做法：

- 显式拼接 `+08:00` 再转 ISO

---

## 6. 查询与分组语义

### 6.1 “今天”
`dashboard/today`、今日统计、今日待办判断等逻辑，统一按：

- `Asia/Shanghai` 的日界线

也就是说：

- 当地 `00:00 ~ 23:59:59` 算同一天
- 后端查询时先算出北京时间当天边界
- 再换成 UTC 范围去查库

### 6.2 计划分组 / 日期分桶
对任务进行 `2026-04-08` 这种日期分组时：

- 必须先把 UTC 时间转回 `Asia/Shanghai`
- 再取 `date()`

不能直接对 UTC 时间裸取日期，否则：

- `2026-04-08T01:30:00Z`
- 仍然属于北京时间 4 月 8 日上午 9:30
- 但若逻辑处理不严谨，可能在部分链路被错误归类

---

## 7. 兼容旧数据的处理

历史上库里已经存在大量 naive 时间字符串，例如：

- `2026-03-19 15:00:00`
- `2026-03-20 10:30:00.000000`

这类旧数据没有显式时区，因此迁移时只能采用约定推断。

当前迁移规则：

> **把旧 naive 时间按 `Asia/Shanghai` 理解，再统一转成 UTC `Z` 格式落盘。**

例如：

- 旧值：`2026-03-20 09:30:00`
- 解释为：`2026-03-20 09:30 Asia/Shanghai`
- 新值：`2026-03-20T01:30:00Z`

### 风险说明
这是一种**约定性迁移**，不是绝对真相。

如果历史上某一批数据本来就是按 UTC 文本手工写进去的，那么迁移会产生偏移。当前判断是：

- `task_center` 的既有使用场景以北京时间为主
- 所以按北京时间解释旧 naive 数据，是总体最合理的默认值

---

## 8. 开发规则

### 8.1 后端规则
- 不要再把时间字段定义成“语义上无时区，但靠注释默认北京时间”
- 所有输入时间统一先标准化成 UTC aware
- 所有服务端生成时间统一使用 UTC aware
- `today`、`history`、`plan group` 等日期语义统一按 `Asia/Shanghai`
- recurrence 计算必须尊重 `timezone` 字段

### 8.2 前端规则
- 不允许业务逻辑直接使用 `slice(0, 10)` 判断是否同一天
- 不允许默认依赖浏览器宿主时区做业务日期分组
- 必须统一复用时间 helper：
  - date key
  - millis compare
  - display formatter
  - `datetime-local` ↔ UTC ISO 转换

### 8.3 聊天 / Agent / 脚本规则
- 非必要，不直接写数据库
- 优先走 `task_center` 自己的 API / 服务层
- 若必须直写库，必须满足：
  - 写入值为 UTC ISO aware 格式
  - 不能写入 naive 字符串
  - 不能混入 `+00:00` / 无 tz / 本地字符串多种风格并存

## 9. 示例

### 示例 1：用户要“明天 09:30 提醒”
用户语义：
- `2026-04-08 09:30 Asia/Shanghai`

数据库：
- `2026-04-08T01:30:00Z`

API 返回：
- `2026-04-08T01:30:00Z`

前端显示：
- `4/8 09:30`

### 示例 2：历史事件创建时间
数据库：
- `2026-04-07T09:08:50.898439Z`

前端显示（北京时间）：
- `4/7 17:08`

---

## 10. 当前结论

`task_center` 未来的时间体系，以这句话为准：

> **DB 存 UTC aware，API 传 ISO 8601 UTC，前端展示与按日判断统一按 Asia/Shanghai。**

如果后续需要支持“用户可切换时区”，可以在此基础上继续扩展；但在那之前，不要再回到 naive datetime 的隐式约定模式。
